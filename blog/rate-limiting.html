Rate limiting

Decide how much each client may ask for, and say no early and cheaply when they ask for more.

4 min readUsed in: 5 · Flash Sale

A rate limiter caps how many requests a client can make in a period of time. It protects you from abuse (scrapers, credential stuffing, a buggy client stuck in a retry loop), keeps one tenant from starving the others, and controls costs when each request calls something expensive. It's also load shedding: turning away excess work cheaply at the door instead of letting it overload the database.

A rejected request gets HTTP 429 Too Many Requests, ideally with a Retry-After header so well-behaved clients know when to come back.

Where it runs and what it counts

  • At the edge or API gateway (NGINX, Envoy, a CDN, a managed gateway): cheapest, and it stops abuse before it reaches your servers.
  • In the service: needed when the limit depends on business data, such as a plan tier or how many orders a user has placed today.
  • The key is what you count per: API key or user ID for logged-in traffic, IP address for anonymous traffic (careful: many users can share one IP behind a NAT), or a combination. Real systems layer several limits, for example 10 per second and 1,000 per hour per user, plus a global cap.

Sliding window counter

Token bucket

A token bucket answers "how big a burst is acceptable?" separately from "what's the long-run rate?". You don't need a timer to add tokens. Store the token count and the time of the last update, and top it up lazily on each request:

def allow(bucket, now): bucket.tokens = min(B, bucket.tokens + (now - bucket.last) * R) bucket.last = now if bucket.tokens >= 1: bucket.tokens -= 1 return True return False

With B = 20 and R = 5 per second, a client can fire 20 requests at once, then gets 5 per second after that. In a multi-threaded server, wrap the read-modify-write in a lock per bucket, or use an atomic compare-and-swap.

Token vs leaky bucket: a token bucket lets bursts through immediately if tokens are saved up. A leaky bucket used as a queue smooths every burst into a steady stream, which suits protecting a downstream system that can only take a fixed rate.

Per-user limits without unbounded memory

One bucket per user, kept forever, grows without limit as new users and IPs appear. Two fixes:

  • Evict idle buckets. A bucket untouched for longer than B ÷ R seconds would be full anyway, so deleting it loses nothing: a new full bucket behaves the same. Keep buckets in an LRU map with a size cap, or set a TTL.
  • Store them in Redis with a TTL, so expiry is automatic.

Distributed rate limiting

With N app servers behind a load balancer, a counter in each server's memory lets a client get N times the limit. The options:

  • Divide the limit by N per server. No coordination, but it's only accurate if the load balancer spreads each client evenly, and it changes whenever N does.
  • A shared store, usually Redis. Every server checks the same counter. For a fixed window, INCR key followed by EXPIRE key 60 on the first increment is enough. For a token bucket, the read-modify-write must be atomic, so run it as a Lua script inside Redis. A plain GET then SET from two servers at once lets both through.
  • Sliding log in Redis with a sorted set: ZREMRANGEBYSCORE to drop old entries, ZADD the new one, ZCARD to count, all in one transaction.
  • Local counters synced periodically: each server counts locally and pushes to the shared store every few hundred milliseconds. It's slightly inaccurate, but it removes a network hop from every request.

Decide what happens when Redis is down. Fail open (allow everything) keeps the product working but drops protection. Fail closed (reject everything) is safer for expensive or security-sensitive endpoints such as login. Many systems fail open with a local in-memory limiter as a backstop.

Telling clients

HTTP/1.1 429 Too Many Requests Retry-After: 12 RateLimit-Limit: 100 RateLimit-Remaining: 0 RateLimit-Reset: 12

Client libraries should back off with jitter when they see 429. Otherwise every rejected client retries at the same moment and the spike repeats.

In the game: there's no rate limiter component yet. In Flash Sale, a limiter is the other half of the queue: the queue absorbs real orders, and a per-user limit stops bots from filling that queue. Every request you reject cheaply at the edge is one the app tier and the database never see.

Interview checklist

  • Say what you're protecting, the key you limit on, and the limits.
  • Pick an algorithm and give a reason: token bucket for bursts, sliding window counter for cheap accuracy.
  • Share counters across servers with atomic operations (Redis plus Lua).
  • Bound memory with TTLs or eviction.
  • Choose fail-open or fail-closed, and return 429 with Retry-After.
